# Development and public updates

Use the locked runtime/package versions and the commands in the repository README. Public code CI performs
the tracked-path/configuration boundary, six new path-policy regression methods, selected saved-run smoke
tests, TypeScript and a production build/private-asset check. It has read-only repository permission, no
configured operational credentials, source requests, database writes, deployment or schedule.
Checkout uses GitHub's ephemeral read-only repository token and does not persist Git credentials.

The first public candidate is checked from its own extracted file tree. Existing local test/review evidence
keeps its original date and source binding. Public smoke/build success is not Browser, primary-database,
source/factual/rights, host, recovery, correction-intake or unattended-publication acceptance.

The local owner keeps a complete project with private append-only history, current state, backlog and review
reports. Those records are not discarded or silently rewritten. New public changes should be staged by
explicit paths, validated and reviewed proportionately, then committed and pushed within owner authority.
The first public push is authorized; code updates do not expand operational or source-publication authority.

The public policy admits original source/schema files and selected synthetic fixtures. It excludes real SSB
fixtures, raw/evidence directories, environment files, internal records and machine-specific evidence tools.
Some historical Python/native tests need those absent private inputs. Arbitrary whole-local check commands
are therefore not advertised as runnable public-clone gates. Do not fabricate replacement research data.

NAS, the actual private SSB attempt and mail remain deferred. The accepted Browser-policy refusal remains;
SSR/native callback tests do not permit a browser/HTTP/transport workaround. Contact-free correction privacy,
source qualification, publication consistency and independent review remain separate requirements.

The pre-publication guard reads the required policy/configuration from immutable stage-0 Git blob identities,
so an unstaged disabled working copy cannot conceal staged activation values. Missing required tracked inputs
fail before acceptance. The exact staged tree still requires disclosure review before commit/push.
